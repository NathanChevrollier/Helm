# Audit complet de Helm — 21 septembre 2026

Périmètre : tout le code (≈ 17 700 lignes) : connexion SSH, sessions, SFTP, nginx, Docker, sauvegardes, déploiement, agent `helmd`, serveur MCP, frontend React, configuration Tauri, CI.
Méthode : lecture ciblée par catégorie de risque, recherche systématique (paniques, interpolation shell, erreurs avalées, boucles d'actualisation, verrous), vérification des cas réels rencontrés (fail2ban, Debian non-root).

**Verdict global** : la base est saine. Les valeurs insérées dans les commandes shell sont toutes validées ou échappées, les secrets vont dans le coffre de l'OS, la CSP est stricte, et nginx est modifié avec sauvegarde, test et restauration. Les problèmes trouvés concernent surtout **la tenue en conditions réelles** : serveurs lents ou injoignables, fichiers corrompus, particularités des distributions. S'y ajoutent **deux fuites de secrets** mineures.

Niveaux : 🔴 à corriger vite · 🟠 important · 🟡 amélioration · 💡 idée.

## 🔴 Priorité 1 : bugs réels à corriger d'abord

### 1. Un serveur qui se connecte bloque tous les autres
- **Où** : [sessions.rs:101-121](../apps/desktop/src-tauri/src/sessions.rs#L101-L121). Le verrou global `connections` reste pris pendant `Connection::connect`.
- **Conséquence** : un serveur injoignable fait attendre toutes les actions sur tous les autres serveurs, jusqu'à 15 s par tentative : terminal, fichiers, vue d'ensemble… Avec plusieurs VPS, l'app paraît figée dès qu'un seul est en panne. C'est précisément quand un serveur tombe qu'on a besoin des autres.
- **Correctif** : un verrou par serveur (`HashMap<String, Arc<tokio::Mutex<()>>>`). Le verrou global ne sert plus qu'à lire ou insérer dans la table. Deux demandes simultanées pour le même serveur partagent alors une seule tentative.

### 2. `helm.json` illisible → tous les profils effacés sans prévenir
- **Où** : [profiles/lib.rs `Store::load`](../crates/profiles/src/lib.rs). `read_json(&path).unwrap_or_default()`.
- **Conséquence** : si le fichier est tronqué (coupure de courant, disque plein, modification manuelle ratée), Helm démarre avec une liste vide. Le prochain enregistrement écrase le fichier, et tous les serveurs, clés d'hôte approuvées, snippets et tunnels sont perdus.
- **Correctif** :
  - si la lecture échoue alors que le fichier existe, le renommer en `helm.json.corrompu-<date>` et afficher un avertissement au démarrage ;
  - garder une copie `helm.json.bak` de la version précédente à chaque écriture ;
  - ajouter un `sync_all()` avant le `rename`.

### 3. Commandes distantes sans délai maximal
- **Où** : [ssh.rs `exec`](../crates/core/src/ssh.rs#L147). Seuls le tableau de bord (20 s) et la vérification SSH des corrections de sécurité ont un délai.
- **Conséquence** : une commande qui ne rend jamais la main bloque l'écran concerné indéfiniment, avec un spinner sans fin. Cas classiques : `df` sur un montage NFS mort, `docker` quand dockerd est bloqué, `apt` qui attend un verrou. Les actualisations suivantes s'empilent derrière.
- **Correctif** :
  - `exec` prend un délai (60 s par défaut) et ferme le canal à l'expiration ;
  - délais plus longs, explicites, pour les opérations lourdes (installation, sauvegarde, `docker compose pull`) ;
  - ajouter aussi un délai sur la phase d'authentification : aujourd'hui seule la connexion TCP est limitée à 15 s.

### 4. L'éditeur de fichiers casse les liens symboliques et change le propriétaire
- **Où** : [sftp.rs `write_text`](../crates/core/src/sftp.rs#L165-L181). L'écriture passe par un fichier temporaire, puis **supprime l'original**, puis renomme.
- **Conséquences** :
  - un lien symbolique (typiquement `sites-enabled/x → sites-available/x`) est remplacé par un fichier normal : le lien est perdu et les deux copies divergent ;
  - le fichier appartient désormais à l'utilisateur SSH, et non plus à son propriétaire d'origine (un fichier de `www-data` peut devenir illisible pour le site) ;
  - pendant un court instant le fichier n'existe pas, et si le renommage échoue il reste absent.
- **Correctif** :
  - résoudre le lien (`canonicalize`) et écrire sur la cible ;
  - utiliser l'extension `posix-rename@openssh.com` (renommage atomique par-dessus l'existant), avec repli sur l'ordre actuel ;
  - si le propriétaire d'origine n'est pas l'utilisateur SSH, passer par l'écriture sudo, qui écrit en place.

## 🟠 Priorité 2 : sécurité

### 5. Agent `helmd` : secrets lisibles par tout utilisateur local
- **Où** : [agent/server.rs:21](../crates/agent/src/server.rs#L21) (socket en `0666`) et [agent/state.rs:43](../crates/agent/src/state.rs#L43) (`status()` renvoie toute la config).
- **Conséquence** :
  - n'importe quel compte du VPS (`www-data` d'un site PHP compromis, par exemple) peut lire l'URL du webhook Discord. Avec elle, on peut poster dans ton salon ;
  - ce compte peut aussi lire le topic ntfy et déclencher `TestNotify` en boucle, ce qui te spamme de notifications.
  - La protection `0640` du fichier de config est donc contournée.
- **Correctif** :
  - retirer les URL de notification du statut, pour n'exposer qu'un booléen « configuré » ;
  - réserver `TestNotify` au propriétaire, avec un socket en `0660` et un groupe `helmd` dont l'utilisateur SSH est membre ;
  - limiter le nombre de connexions simultanées au socket, car aujourd'hui chaque connexion crée un thread.

### 6. Écrasement silencieux d'une modification concurrente
- **Où** : [FileEditor.tsx](../apps/desktop/src/components/FileEditor.tsx) et `fs_write`.
- **Conséquence** : si le fichier change sur le serveur pendant que tu l'édites (déploiement, autre session, certbot), l'enregistrement écrase cette modification sans le dire.
- **Correctif** : mémoriser la date de modification et la taille à l'ouverture, puis les comparer avant d'écrire. En cas d'écart, proposer « Voir les différences / Écraser / Recharger ». Même principe pour l'éditeur nginx.

### 7. Masquage des secrets MCP incomplet
- **Où** : [mcp/mask.rs](../crates/mcp/src/mask.rs). Le masquage ne regarde que le **nom de la clé** d'une ligne `CLE=valeur` ou `cle: valeur`.
- **Ce qui passe aujourd'hui vers l'IA** :
  - la syntaxe PHP : `define('DB_PASSWORD', 'secret');` dans `wp-config.php`, sous `/var/www`, autorisé ;
  - les mots de passe dans une URL dont la clé est anodine : `url: mysql://user:motdepasse@db` ;
  - les jetons dans les logs d'accès nginx : `GET /api?token=abc…`, ou `Authorization: Bearer …` au milieu d'une ligne ;
  - les jetons reconnaissables à leur préfixe, même sans clé sensible : `sk_live_`, `ghp_`, `github_pat_`, `AKIA…`, `xox[bp]-`, JWT `eyJ…`.
- **Correctif** : ajouter un second passage par motifs : identifiants dans les URL (`://[^:]+:[^@]+@`), paramètres `token`, `key`, `secret` ou `password` dans les requêtes, `Bearer \S+`, préfixes connus, `define('…PASS…'`. Tests unitaires pour chaque cas.

### 8. MCP `read_file` suit les liens symboliques
- **Où** : [mcp/lib.rs `readable`](../crates/mcp/src/lib.rs#L98). La vérification porte sur le chemin demandé, pas sur sa cible.
- **Conséquence** : un lien `/opt/app/x → /etc/shadow` (ou vers une clé) passe le filtre, et la lecture se refait en sudo si elle échoue. Le masquage des clés privées limite les dégâts, mais pas pour `/etc/shadow`.
- **Correctif** : résoudre le chemin (`readlink -f`) côté serveur, puis appliquer les listes autorisée et interdite au chemin réel.

### 9. Collage multi-lignes sans confirmation
- **Où** : [TerminalPane.tsx](../apps/desktop/src/components/TerminalPane.tsx), clic droit et Ctrl+Maj+V.
- **Conséquence** : coller un bloc de plusieurs lignes l'exécute ligne par ligne immédiatement. Une erreur de presse-papiers peut lancer une commande destructrice. Avec la diffusion de la saisie active, le problème touche tous les serveurs d'un coup.
- **Correctif** : si le texte contient un saut de ligne et que le shell n'est pas en mode « bracketed paste », demander confirmation avec un aperçu. Demander toujours confirmation quand la diffusion est active.

### 10. Autres points de sécurité
- **Liens cliquables du terminal** : restreindre l'ouverture à `http(s)://`. Aujourd'hui, toute URL détectée est transmise à l'opener.
- **Déploiement GitHub** : quiconque peut modifier le dépôt peut déclencher `helm-deploy` en root, et l'image tirée peut monter l'hôte. C'est inhérent au principe, mais il faut l'écrire dans l'interface, et proposer la rotation et la révocation visibles de la clé.
- **App déverrouillée** : Helm ouvert donne un accès root à tous les serveurs. Proposer en option un verrouillage après inactivité (Windows Hello ou mot de passe), qui ferme les connexions.

## 🟠 Priorité 3 : robustesse et confort au quotidien

### 11. Un terminal lent bloque la saisie dans tous les autres
[sessions.rs:179-189](../apps/desktop/src-tauri/src/sessions.rs#L179-L189) : le verrou `terminals` reste pris pendant l'envoi. Si un canal est saturé (sortie énorme, réseau lent), les frappes dans les autres terminaux attendent.
**Correctif** : cloner le `ChannelWriteHalf`, ou stocker des `Arc`, puis relâcher le verrou avant l'envoi. Au passage, retirer de la table les terminaux fermés côté serveur, qui y restent aujourd'hui (petite fuite).

### 12. Notifications d'erreur en rafale
[Processes.tsx:21](../apps/desktop/src/views/monitoring/Processes.tsx#L21) et [Services.tsx:19](../apps/desktop/src/views/monitoring/Services.tsx#L19) : quand la connexion tombe, une notification d'erreur apparaît toutes les 5 s.
**Correctif** : afficher l'erreur dans la vue (comme Overview) plutôt qu'en notification, et suspendre l'actualisation automatique tant que la connexion est coupée.

### 13. Pas de journal local
Aucun fichier de logs côté app. Quand quelque chose échoue chez toi, on n'a que la notification.
**Correctif** : `tauri-plugin-log`, avec des fichiers tournants dans le dossier de l'app, sans aucun secret, et un bouton « Ouvrir les journaux » dans Réglages.

### 14. Le faux VPS masque les bugs des vrais serveurs
Le testenv se connecte en root sur Ubuntu. C'est pour ça que le bug du PATH (`/usr/sbin`) et la question tmux prématurée ne sont apparus que sur ton vrai VPS.
**Correctif** : un deuxième profil de test fidèle au vrai VPS :
- Debian ;
- utilisateur non-root avec sudo à mot de passe ;
- fail2ban actif ;
- port SSH non standard ;
- nginx et ufw installés, sans tmux.

### 15. Timeout ambigu : suggérer un bannissement fail2ban
L'incident du 21/09 est parti d'un simple « délai dépassé ». Quand la connexion expire alors que le serveur répond en HTTP ou sur son port 80/443, Helm peut afficher : « Ton IP est peut-être bannie par fail2ban : essaie depuis un autre réseau ou la console de ton hébergeur ». Une connexion TCP rapide sur le port 443 suffit à lever l'ambiguïté.

### 16. Actualisations automatiques qui se chevauchent
[Docker.tsx:119-131](../apps/desktop/src/views/Docker.tsx#L119-L131) : `docker stats` prend souvent 2 à 3 s. Avec beaucoup de conteneurs, il dépasse l'intervalle de 5 s, et les appels s'empilent.
**Correctif** : un garde « déjà en cours » comme dans Overview. Suspendre aussi toutes les actualisations quand la fenêtre est réduite (`document.hidden`).

### 17. Deux instances de Helm en même temps
Rien n'empêche d'ouvrir Helm deux fois. Les tunnels entrent alors en conflit de port, et la dernière instance qui enregistre écrase les modifications de l'autre dans `helm.json`.
**Correctif** : `tauri-plugin-single-instance`, qui remet la fenêtre existante au premier plan.

### 18. Petits défauts
- **Cache uid/gid** ([sessions.rs:62](../apps/desktop/src-tauri/src/sessions.rs#L62)) jamais rafraîchi : un utilisateur créé après la connexion s'affiche avec un numéro. À vider à la reconnexion.
- **Téléchargements** : un nom de fichier Linux contenant `:` `?` `*` `"` `<` `>` `|` est invalide sous Windows et fait échouer tout le dossier. Il faut remplacer ces caractères et prévenir. Un fichier local du même nom est écrasé sans demander.
- **Lecture sudo** (`read_file_sudo`) : pas de limite de taille ni de détection des fichiers binaires, contrairement à la lecture SFTP. Un gros log ouvert en sudo peut geler l'éditeur.

## 🟡 Compatibilité avec d'autres serveurs

19. **Distributions** : les corrections de sécurité (ufw, fail2ban, mises à jour automatiques) supposent `apt`. Sur Rocky, Alma ou Fedora, elles échouent. Il faut détecter la famille (`/etc/os-release`) et utiliser dnf et firewalld, ou masquer ces corrections.
20. **Serveurs web** : seuls nginx et certbot sont gérés. Caddy, Traefik (fréquent avec Docker) et Apache n'apparaissent pas dans Sites : il faudrait au moins les détecter et l'afficher.
21. **Conteneurs** : Docker uniquement. Podman et Docker rootless ne sont pas détectés.
22. **SSH** : pas de rebond par un bastion (ProxyJump), pas de certificats SSH, pas d'import de `~/.ssh/config`. Seul l'import PuTTY existe.
23. **Agent** : seulement Linux x86_64 et arm64 avec systemd. Afficher clairement pourquoi l'installation est impossible ailleurs.
24. **Sudo** : un serveur configuré en `requiretty` refuse `sudo -S` sans pseudo-terminal. Il faut détecter ce message et l'expliquer.

## 🟡 Qualité, tests, distribution

25. **Tests frontend** : aucun. Commencer par Vitest sur `store.ts` (`ensureConnected`, suspension après échec d'authentification) et sur les utilitaires d'`api.ts`.
26. **Tests de bout en bout** : les scripts `examples/smoke*.rs` et les scénarios Playwright ne tournent qu'à la main. Ajouter en CI un job qui démarre le testenv, en Docker sur Linux, puis lance les smoke tests.
27. **Audit des dépendances** : ajouter `cargo audit` (ou `cargo deny`) et `pnpm audit` à la CI.
28. **Mises à jour** : pas de mise à jour intégrée. Ajouter `tauri-plugin-updater` avec des releases GitHub signées. L'app pourra aussi signaler un agent `helmd` plus ancien que l'app et proposer de le mettre à jour.
29. **Signature Windows** : l'installeur n'est pas signé, d'où l'avertissement SmartScreen. Solutions : certificat de signature de code, ou Azure Trusted Signing (peu coûteux).
30. **Sauvegarde des réglages Helm** : exporter et importer `helm.json` (profils, snippets, tunnels) dans un fichier chiffré, sans secrets du coffre ou avec en option. Utile pour changer de PC, et complémentaire du point 2.

## 💡 Idées de fonctionnalités

**Directement liées à ce qu'on a vécu**
- **Panneau fail2ban** dans Sécurité :
  - IP bannies par jail, bouton « Débloquer » ;
  - liste `ignoreip` modifiable, avec « Ajouter mon IP actuelle » ;
  - durée et nombre d'essais visibles.
- **Assistant « Je n'arrive plus à me connecter »** : il teste le DNS, le port, la bannière SSH et l'accès HTTP, puis conclut (serveur éteint, IP bannie, clé refusée, pare-feu).

**Terminal**
- Recherche dans le terminal (addon xterm `search`) et zoom de la police (Ctrl+molette).
- Enregistrement et relecture de session (format asciicast).
- Historique des commandes par serveur, avec recherche dans la palette Ctrl+K.

**Administration**
- Gestionnaire de tâches planifiées (crontab et timers systemd).
- Gestion des utilisateurs et des clés `authorized_keys`, avec révocation en un clic.
- Vue pare-feu : règles ufw lisibles, et ports exposés croisés avec les conteneurs.
- Vérification DNS des sous-domaines (A/AAAA pointant bien vers le VPS) et de l'expiration du domaine.

**Confort**
- Notifications natives Windows pour les alertes quand l'app est ouverte.
- Thème clair et raccourcis configurables.
- Aperçu des différences avant d'enregistrer, dans l'éditeur de fichiers comme dans l'éditeur nginx.
