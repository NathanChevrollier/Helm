# Audit sécurité et optimisation de Helm — 26 septembre 2026

Périmètre :
- application de bureau : backend Tauri/Rust, crates `core`, `profiles`, `mcp`, `ai`, `agent` ;
- frontend React refondu ;
- serveur `helm-sync` (synchronisation et relais de partage) ;
- bot Discord ;
- configuration Tauri et CI.

Méthode, dans cet ordre :
1. Relecture ciblée des frontières de confiance :
   - l'interface et le backend ;
   - les fichiers et codes de partage reçus d'un tiers ;
   - le relais de partage ;
   - le fournisseur d'IA ;
   - le serveur administré ;
   - la chaîne de publication.
2. Recherche systématique : commandes exécutées sans contrôle, fichiers temporaires, sérialisation sur le fil principal.
3. Pour chaque correctif, un test qui reproduit l'attaque ou le défaut avant de le fermer.

**Verdict global** : les fondations restent saines.
- Les secrets sont rangés dans le coffre de l'OS.
- Les valeurs insérées dans une commande shell sont échappées.
- Les échanges de synchronisation et de partage sont chiffrés de bout en bout.
- nginx n'est modifié qu'avec sauvegarde, test puis restauration en cas d'échec.

Les failles trouvées ne sont pas des erreurs de code isolées : ce sont **des hypothèses de confiance trop larges**.
- Le verrouillage ne protégeait que l'affichage.
- Un partage importé était traité comme venant de soi-même.
- Le relais pouvait rejouer une frappe.
- La détection des commandes et requêtes sensibles se contournait avec une simple variante d'écriture.

Tous les points 🔴 et 🟠 sont corrigés dans cette branche. Les points restants sont listés à la fin, avec les options possibles.

Niveaux : 🔴 critique · 🟠 élevé · 🟡 moyen · ⚪ faible / à décider.

## 🔴 1. Verrouillage appliqué côté backend

- **Où** : `src-tauri/src/lib.rs`, `commands/workspace.rs`.
- **Constat** : l'état `LOCKED` existait côté Rust, mais aucune commande ne le vérifiait. L'écran de verrouillage n'était qu'un calque d'interface. Sur un poste laissé verrouillé, n'importe quel appel `invoke` restait possible, par exemple depuis les outils de développement d'une build de debug ou par un script injecté :
  - `fs_read` ;
  - `term_write` ;
  - `servers_list` ;
  - `settings_export` avec les secrets.

  Deux problèmes s'ajoutaient :
  - `app_lock_get` renvoyait l'empreinte PBKDF2 à l'interface ;
  - `app_lock_set` acceptait n'importe quelle chaîne, y compris une empreinte à 1 itération.
- **Correctif** :
  - `invoke_handler` est enveloppé par `guarded()`. Quand Helm est verrouillé, toute commande est refusée, sauf une courte liste blanche : `app_version`, `app_is_locked`, `app_unlock`, `app_lock_engage`, `ui_state_get`, `store_warning`, `term_resize`. Une commande ajoutée plus tard est donc protégée d'office.
  - L'empreinte est validée : format `pbkdf2`, au moins 100 000 itérations, sel d'au moins 16 octets, 32 octets d'empreinte.
  - Elle ne quitte plus le backend : `app_lock_get` répond seulement « configuré ».
  - Les essais de déverrouillage sont sérialisés, avec un délai après chaque échec, et vérifiés hors du fil des commandes.
  - Côté interface, un délai croissant s'ajoute après trois échecs, et les sondages s'arrêtent pendant le verrouillage.
- **Test** : `lock_password_format` (empreinte forte acceptée, faible et sel court refusés).

## 🔴 2. Import de réglages et de partages

- **Où** : `crates/profiles/src/export.rs`, fonction `import`.
- **Constat** : un fichier `.helm` ou un code `helm-share:` vient souvent de quelqu'un d'autre. Deux abus étaient possibles.
  1. `known_hosts.extend(...)` **remplaçait l'empreinte d'une clé d'hôte déjà approuvée**. Un partage piégé faisait donc accepter en silence la clé d'un serveur intercepté.
  2. Un serveur reçu avec le **même identifiant** qu'un serveur existant le remplaçait entièrement, adresse comprise. Or les mots de passe et passphrases sont rangés dans le coffre sous cet identifiant. À la connexion suivante, ils partaient vers l'adresse de l'attaquant.
- **Correctif** :
  - Une empreinte déjà approuvée n'est jamais remplacée (`entry().or_insert`).
  - Un serveur de même identifiant mais d'hôte, port ou utilisateur différent reçoit un nouvel identifiant et s'ajoute à côté. Tout ce qui y fait référence dans le contenu reçu suit le nouvel identifiant : tunnels, rebond, bureaux distants, constats ignorés, secrets.
  - Le bilan d'import indique ces deux cas, et l'interface les affiche.
  - La synchronisation entre ses propres postes (phrase de passe commune) garde volontairement la fusion complète.
- **Tests** :
  - `import_never_replaces_a_pinned_host_key` ;
  - `import_does_not_redirect_an_existing_server`.

## 🟠 3. Relais de partage de terminal : rejeu et réflexion

- **Où** : `commands/share.rs`.
- **Constat** : les messages étaient chiffrés (AES-256-GCM) sans données associées. Un relais `helm-sync` compromis ne lisait rien, mais pouvait :
  - **rejouer** une frappe d'invité en mode contrôle (par exemple `rm …⏎` exécuté deux fois) ;
  - **renvoyer à l'hôte** un message de l'hôte comme s'il venait d'un invité.
- **Correctif** :
  - Chaque message porte un identifiant d'émetteur aléatoire et un compteur croissant.
  - Ces deux valeurs et le **sens du message** sont authentifiés dans l'AAD.
  - Le récepteur refuse un compteur qui n'avance pas, ainsi qu'un message de l'autre sens.
  - Le nombre d'émetteurs suivis est borné.
  - Le format passe en v2, incompatible avec les invitations des versions précédentes.
- **Test** : `relay_cannot_replay_or_reflect`.

## 🟠 4 à 6. Assistant IA

- **`read_file`** (`commands/assistant.rs`)
  - Constat : la règle de chemins était vérifiée sur le chemin demandé, pas sur sa cible. Un lien `/opt/x → /etc/shadow` ouvrait la lecture de la cible. Le serveur MCP résolvait déjà ce cas, pas l'assistant intégré.
  - Correctif : résolution par `readlink -f` (fonction `helm_mcp::real_path`, rendue publique), puis nouvelle vérification.
- **`dangerous()`**
  - Constat : une recherche de sous-chaînes (`"rm -rf"`) laissait passer, même en mode autonome :
    - `rm -fr` ;
    - `rm -r -f` ;
    - `sudo /bin/rm --recursive --force` ;
    - `find … -delete` ;
    - `curl … | sh` ;
    - `echo … | base64 -d | bash` ;
    - `chmod -R` ;
    - `crontab -r` ;
    - `docker compose down -v` ;
    - `mkfs.ext4`.
  - Correctif :
    - la commande est normalisée puis découpée sur `;`, `&&`, `||`, `|` et les retours à la ligne ;
    - `sudo`, `env` et les chemins d'exécutables sont retirés ;
    - les options de `rm` sont lues une à une ;
    - chaque programme a sa règle.
  - Test : `dangerous_commands` (19 variantes à bloquer, 7 commandes courantes à laisser passer).
- **Contexte joint et adresse d'API**
  - Constat : le contexte envoyé automatiquement (sortie de terminal…) partait sans masquage. Une adresse `http://` vers un fournisseur distant faisait circuler la clé d'API et les données en clair.
  - Correctif :
    - le contexte est masqué comme les sorties d'outils ;
    - `helm_ai::check_base_url` exige `https://`, sauf pour la machine locale ou un réseau privé (Ollama, LM Studio) ;
    - la règle est vérifiée à l'enregistrement **et** à chaque appel.
  - Test : `base_url_must_be_encrypted_unless_local`.

## 🟠 7. Installation de l'agent `helmd`

- **Où** : `commands/monitoring.rs`, `crates/core/src/agent.rs`.
- **Constat** : le binaire embarqué suivait ce trajet :
  1. écriture dans `%TEMP%/helm-agents/helmd-<arch>`, un chemin prévisible, partagé sous Linux ;
  2. relecture depuis le disque, puis calcul du SHA-256 ;
  3. copie dans un second dossier prévisible, puis envoi.

  Un autre compte local pouvait substituer le fichier entre l'écriture et la relecture. Le serveur installait alors en root un programme au SHA « correct ».
- **Correctif** :
  - l'empreinte est calculée sur les octets embarqués ;
  - le binaire est envoyé depuis la mémoire (`sftp::write_bytes`), sans fichier local.

## 🟠 8. Requêtes SQL « en lecture seule »

- **Où** : `crates/core/src/db.rs` (`is_read_only`), `views/Databases.tsx`.
- **Constat** : seul le premier mot comptait. Les requêtes suivantes s'exécutaient **sans confirmation dans l'interface et sans entrée au journal d'actions** :
  - `SELECT 1; DROP TABLE users` ;
  - `WITH d AS (DELETE … RETURNING *) SELECT …` ;
  - `SELECT … INTO OUTFILE` ;
  - `EXPLAIN ANALYZE UPDATE …`.
- **Correctif** :
  - La règle devient : une seule instruction, un premier mot de lecture, **aucun** mot d'écriture ailleurs.
  - Chaînes, commentaires, identifiants entre guillemets et `$$…$$` sont écartés avant l'analyse.
  - `#` et l'antislash ne sont pas interprétés : c'est un commentaire et un échappement pour MySQL, pas pour PostgreSQL. Les interpréter pouvait masquer une instruction ; ne pas les interpréter ne peut que provoquer une confirmation de trop.
  - La même règle est appliquée côté interface (`lib/sql.ts`).
- **Tests** : `read_only_detection` (Rust) et `lib/sql.test.ts` (TypeScript), avec les mêmes cas.

## 🟠 9. Console Redis

- **Où** : `crates/core/src/redis.rs`.
- **Constat** : la liste noire ne couvrait que `FLUSHALL`, `SHUTDOWN`, etc. Elle laissait passer :
  - `CONFIG SET dir` suivi de `SAVE`, le chemin classique pour écrire un fichier arbitraire sur le serveur ;
  - `MODULE LOAD` ;
  - `EVAL` ;
  - `REPLICAOF`, qui envoie la base vers une machine tierce ;
  - `MIGRATE`.
- **Correctif** :
  - ces commandes sont refusées, avec aussi `SCRIPT`, `FUNCTION`, `SAVE`/`BGSAVE`, `RESTORE` et `CLUSTER` ;
  - certaines sous-commandes le sont aussi (`CONFIG SET/REWRITE`, `ACL SETUSER`, `CLIENT KILL`) ;
  - `CONFIG GET` et `ACL WHOAMI` restent permis.
- **Test** : `console_refuses_dangerous_commands`.

## 🟡 10. Fichiers `.vv` (SPICE) et `.rdp`

- **Constat** : le fichier `.vv` peut contenir le mot de passe SPICE. Il était écrit avec les droits par défaut, puis restreint en 0600, ce qui laissait une fenêtre où il était lisible par tous.
- **Correctif** : `write_private` crée les fichiers `.vv` et `.rdp` en 0600 dès l'ouverture.

## 🟡 11. Politique de sécurité du contenu (CSP)

- **Constat** : `connect-src` contenait `ws:`, qui autorise une WebSocket vers n'importe quel hôte. Un script injecté pouvait donc exfiltrer des données.
- **Correctif** : il ne reste que `ws://127.0.0.1:*` pour les ponts locaux RDP et VNC.

## 🟡 12. Chaîne de publication (CI)

- **Actions tierces** : elles sont désormais épinglées par SHA de commit, avec la version en commentaire. Un tag déplacé ne peut plus injecter de code dans la release signée.
- **Droits** : `release.yml` accorde maintenant la lecture seule par défaut. L'écriture n'est donnée qu'aux jobs `draft`, `build`, `sign-windows` et `publish`.
- **CLI de signature** : elle est fixée à une version exacte (`@tauri-apps/cli@2.11.5`, et non plus `@2`). Elle manipule la clé privée de mise à jour.

## 🟡 13. `helm-sync`

- **Constat** :
  - aucune limite d'envoi ;
  - aucun plafond de sessions de partage, ni par jeton ni au total ;
  - la file des frappes d'invités vers l'hôte était non bornée ;
  - chaque requête sans jeton valide dormait 400 ms, sans limite de concurrence : un flot de requêtes accumulait des milliers de tâches.
- **Correctif** :
  - 60 envois par minute et par espace ;
  - 30 ouvertures de partage par heure ;
  - 8 partages simultanés par espace et 512 au total ;
  - file des frappes bornée à 256 messages, avec contre-pression sur l'invité ;
  - 64 refus différés au plus en même temps, les suivants refusés tout de suite.
- **Test** : `limiter_counts_per_key_and_window`.

## 🟡 14. Bot Discord

- **Constat** :
  - chaque formulaire crée une issue GitHub, sans aucune limite par membre : spam, et épuisement du quota du jeton GitHub ;
  - `@quelqu'un` et `#123` saisis sur Discord notifiaient de vrais comptes GitHub ou liaient d'autres issues.
- **Correctif** :
  - `Cooldown` limite à un retour par minute et cinq par heure et par personne ;
  - `neutralize()` insère un caractère invisible qui casse les mentions et références.
- **Tests** : `cooldown.test.ts`, `neutralize`.

## 🟡 15 à 17. Performance

- **Fil principal** : les commandes Tauri synchrones s'exécutent sur le fil principal. L'interface se figeait donc pendant :
  - l'export, le partage et l'import chiffrés (PBKDF2, 600 000 tours) ;
  - la lecture d'un fichier du PC jusqu'à 512 Mo.

  Ces commandes passent en `#[tauri::command(async)]`.
- **Coffre** : `servers_list`, appelée à chaque actualisation, lisait 3 secrets par serveur, et une lecture Secret Service passe par D-Bus. La présence des secrets est désormais mise en cache (`secrets::has`). Le cache est tenu à jour par les écritures du processus, seul à écrire dans le coffre de Helm.
- **Sauvegarde de l'espace de travail** : le store change sans cesse (notifications, état des serveurs, transferts). Le JSON n'est plus recalculé que lorsqu'une partie sauvegardée change de référence.
- **Déjà en place, vérifié** :
  - Monaco, Terminal, Supervision et le client RDP sont chargés à la demande (chunks séparés) ;
  - les listes longues passent par `DataTable`, virtualisé au-delà de 200 lignes ;
  - les journaux utilisent `content-visibility: auto` ;
  - les sondages sont en pause quand la fenêtre est masquée, et désormais aussi quand Helm est verrouillé.

## ⚪ Points ouverts, à décider

18. **Mot de passe RDP via `cmdkey` (Windows)** — `rdp.rs`, lancement de `mstsc`.
    - Constat : le mot de passe passe en argument de `cmdkey /pass:`. Il est visible un court instant dans la liste des processus pour le même utilisateur. L'effet est le même que « Mémoriser mes informations » de mstsc.
    - Options :
      - appeler directement `CredWriteW` (API Windows) ;
      - ou utiliser seulement le client RDP intégré, qui ne passe pas par `cmdkey`.
19. **Mot de passe RDP ou VNC transmis au client WASM** : c'est inhérent au client intégré (le protocole l'exige côté client). Le pont local est protégé par un jeton aléatoire, et la CSP n'autorise que `127.0.0.1`.
20. **Clé d'hôte indexée par `hôte:port`** : un serveur qui change légitimement de type de clé est vu comme une clé modifiée. C'est le comportement le plus prudent. Une indexation par `hôte:port:type` réduirait les faux positifs, au prix d'une migration.
21. **`style-src 'unsafe-inline'`** : Monaco, xterm et les styles dynamiques de React l'exigent. Le risque résiduel reste faible, puisque `script-src` est strict.
22. **`MAX_CLIENTS` de `helmd`** : la vérification et l'incrément ne sont pas atomiques (`crates/agent/src/server.rs`). Deux connexions simultanées peuvent dépasser la limite d'une unité. Le socket n'est accessible qu'en local, avec des droits restreints. Correctif simple si souhaité : `fetch_update`.
23. **Limite d'essais par adresse IP sur `helm-sync`** : derrière nginx, toutes les requêtes arrivent de `127.0.0.1`, et une limite par IP bloquerait tout le monde. Les jetons font au moins 24 caractères aléatoires, ce qui rend la recherche au hasard hors de portée. Pour ajouter une vraie limite par client, il faudrait se fier à `X-Forwarded-For` derrière un proxy déclaré.
